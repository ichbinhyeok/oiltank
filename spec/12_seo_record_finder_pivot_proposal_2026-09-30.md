# Oil Tank Route — SEO 중심 기록 조회 서비스 피벗 제안

작성: 2026-09-30 · 상태: 사용자 구현 승인 / 로컬 구현 및 검증 중, 미배포

사용자가 “다 이제 작업해”로 구현을 승인했다. 아래 본문은 승인 당시 설계와 제약의 기록이며, ‘승인 전’이라는 과거 표현보다 이 상태가 우선한다. 실제 통과·보류 후보와 구현 범위는 `ops/2026-09-30_record_finder_launch_inventory.md`가 최신이다. 로컬 변경을 배포 완료로 해석하지 않는다. 새 지역 대행 수락·요금 변경·기관 자동 발송은 승인하거나 구현하지 않는다.

## 1. 결정 요약

**‘탱크 서류 조사를 맡기는 사이트’에서 ‘탱크 기록을 찾고 다음 조치를 준비하는 서비스’로 공개 제품의 중심을 이동한다.** 사람에게 맡기는 조사 서비스는 없어지는 것이 아니라, 직접 해결하지 못한 사용자를 위한 선택지로 남긴다.

목표는 페이지 숫자나 위젯 사용량이 아니다. 실제 기록을 찾으려는 검색으로 들어온 사람이, 현재 위치와 찾는 서류에 맞는 공식 경로·필요 식별자·다음 작업을 얻는 것이다. 일부는 공식 자료를 찾고 떠나도 제품 성공이다. 그러나 그 자체가 매출 성공은 아니며, 기존 조사 의뢰와 유료 수요는 별도 측정한다.

이번 변화는 브랜드·도메인·전체 코드를 다시 만드는 피벗이 아니다. **유입 주제, 공개 서비스 기능, 지역 범위, 정보 구조를 함께 바꾸는 피벗**이다.

### 고정 조건

- 유입 전략은 SEO. 별도 영업, 제휴 영업, 광고, 구매 링크 캠페인 제외.
- 몇 페이지로 시작해 클릭이 날 때까지 기다리는 출시 방식 제외. 검증된 넓은 범위와 완결된 작업 흐름을 한 제품으로 출시.
- 검색량을 모른다고 시장이 없다고 단정하지 않는다. 반대로 공식 자료가 있다고 검색 수요가 검증됐다고 말하지 않는다.
- 기존 도메인, 의미 있는 URL, 계산기 20개, 사설 케이스 저장소와 의뢰 기록 보존.
- 개인정보와 문서는 공개 검색 페이지·사이트맵·분석 도구에 넣지 않는다.
- 조회 실패/미등재/접근 실패는 탱크 부재·안전·적법성 판정이 아니다.

## 2. 전제 재검토

### 확인한 사실

- Septic은 기관명, 주별 조회, 카운티 기록 등 여러 입구에서 검색 클릭을 얻었다. 2026-09-01~27 TDEC 157클릭, 카운티 페이지군 210클릭, 클릭 발생 카운티 페이지 88개. 출처와 집계 차이는 `ops/2026-09-30_septic_seo_comparison.md` 참고.
- 현재 Oil Tank에는 지역 16개, 문제 5개, 공식 링크, 식별자 안내, 복사 가능한 요청문, 조사 의뢰 기능이 있다. 이를 없는 것처럼 다시 만들지 않는다.
- Septic도 현재 조사 의뢰를 앞에 보여준다. CTA 순서만으로 두 사이트의 SEO 차이를 설명할 수 없다.
- 기존 Oil Tank 지역 선택은 공식 절차 차이에 기반했으며 검색량으로 최적화된 결과가 아니다.

### 아직 모르는 것

- Oil Tank 관련 각 기록 검색어의 미국 월간 검색량·경쟁 난도·실제 전환 가치.
- 기관별 위젯이 순위나 클릭을 얼마나 늘릴지.
- 기존 도메인의 경쟁력, 외부 링크, 검색 품질 평가가 현재 격차에 기여하는 정도. 링크 구매나 도메인 교체를 결론으로 삼지 않는다.
- 표본이 충분한 의뢰 전환율과 지불 의사. 지금 검색 유입이 작다는 사실로 가격/전환 실패까지 진단하지 않는다.

### 핵심 수정

**‘NJ·NY 주택 거래 중 서류가 막힌 사람’만 입구로 삼지 않는다. ‘어느 지역이든 해당 기록을 직접 찾으려는 사람’까지 유입 대상을 넓힌다.** 단, 검증된 기록 접근 범위 안에서만 제공한다. 모든 미국 주소의 탱크 이력을 조회한다고 약속하지 않는다.

## 4. 제품의 중심: Record Finder + 작업지

공개 약속 후보: **Find the right oil tank records—and know what to do next.**

‘주소 입력하면 모든 기록을 찾아준다’는 문구는 사용하지 않는다. 초기 제품은 **관할·문서별 조회 경로 찾기와 요청 준비**이며, 특정 데이터 연결이 실제 제공될 때만 그 범위를 별도로 표시한다.

### 대표 사용 흐름

```text
지역/기관/문서 검색으로 방문
  → 페이지에서 해당 작업의 답과 공식 출처 즉시 확인
  → 찾는 문서와 관할 선택
  → 적용 경로 + 검색 식별자 + 공식 조회 단계
  → 공식 시스템에서 직접 조회
  → 찾음 / 결과 없음 / 접근 실패 / 잘못된 기관 / 요청 대기
  → 각 상태에 맞는 작업지·요청문·다음 단계
  → 필요할 때만 기존 조사 의뢰로 이어짐
```

### 반드시 한 번에 제공할 기능

1. **경로 선택:** 주·municipality·문서 종류를 기준으로 공식 소유 기관을 안내. 우편주소 도시명이나 ZIP만으로 행정 관할을 확정하지 않는다. 모호하면 확인 방법과 수동 선택을 제공한다.
2. **문서 구분:** 제거 허가, 완료 검사, 폐쇄 확인서, 환경 사건 기록, NFA를 구분한다. 서로 대체할 수 있다고 표시하지 않는다.
3. **조회 작업지:** 주소, parcel/block/lot, 사건번호, 예상 시기 등 필요한 검색 키를 로컬에서 준비하고 복사/인쇄한다. 주소는 필수가 아닌 작업지 입력이며 초기에는 자동 지오코딩을 출시 의존성으로 삼지 않는다.
4. **상황별 요청문:** 공식 채널에서 필요한 기록 종류·기간·식별자만 포함한 초안을 준비한다. 발송이나 접수로 표시하지 않는다.
5. **실패 후 안내:** ‘사이트가 막힘’과 ‘온라인 결과가 없음’과 ‘기관의 공식 no-record 회신’을 별도 상태로 처리한다.
6. **일관된 완료 화면:** 확인한 출처, 아직 확인하지 않은 출처, 얻어야 할 서류, 다음 행동을 보여준다. 사용자가 선택한 ‘찾음’은 자기 보고이지 자료 검증이 아니다.
7. **저장·재개:** 기본은 탭 세션. 사용자가 명시적으로 저장할 때만 기기에 최대 7일 저장하고 삭제 기능 제공. 개인 주소를 담은 공개 공유 URL은 생성하지 않는다.

자동 OCR, AI 법적 판단, 전국 자동 파일 수집, 자동 기관 메일은 첫 출시 필수 기능이 아니다. 경로 안내의 정직성과 완결성이 화려한 자동화보다 먼저다.

## 5. SEO 정보 구조: 지역 × 문제 무한 곱셈 금지

검색 입구는 세 가지이며, 각 페이지는 자체적으로 유용해야 한다.

| 페이지 유형 | 검색 작업 | 고유하게 제공해야 할 결과 |
| --- | --- | --- |
| 기관·문서 | NJDEP NFA, Oregon HOT, Nassau verification 등 | 실제 조회 위치, 문서/프로그램 선택, 식별자, 누락 범위, 실패 후 경로 |
| 지역 | 해당 municipality/county의 탱크 관련 기록 | 담당 기관 차이, 로컬 파일 종류, 요청 절차, 상위 기관과의 경계 |
| 문제 | 제거했다는데 서류 없음, 검색 결과 없음, 서류 충돌 | 어떤 기록부터 구하고 무엇을 대조해야 하는지 |

검색에 노출시킬 핵심 답·공식 경로·한계는 모두 서버 렌더링한다. 위젯은 이 답을 개인 작업에 적용하는 기능이지, 검색엔진에만 보여줄 숨은 내용이 아니다. 페이지마다 별도 입력 폼을 복제하지 않고 한 경로 모델을 사용한다.

**중복 방지:** 같은 기관·같은 문서·같은 절차면 표현이 다른 키워드라도 하나의 대표 URL. 예: Nassau 기존 페이지를 강화하고 비슷한 verification 페이지를 새로 만들지 않는다. 기관 검색과 지역 조회가 정말 다른 작업일 때만 분리한다.

## 6. 지역 전략: 행정구역 숫자보다 기록 구조

Septic의 카운티 단위를 그대로 복사하지 않는다. Oil Tank은 주 환경기관, 시 소방/건축기관, 카운티 보건부가 서로 다른 기록을 가진다. **실제 기록 소유 기관과 작업이 페이지 단위**다.

### 첫 출시 후보 범위

| 범위 | 제공할 작업 | 현재 확인 수준 | 출시 전 추가 확인 |
| --- | --- | --- | --- |
| NJ | NFA/환경 자료 + 기존 municipal permits | 기존 원천·공식 NFA 경로 확인 | 조회별 선택 항목·구문, local 범위 확장 |
| NY | DEC 사건/문서 + Nassau 확인서 + town 기록 | 기존 원천과 Nassau 경로 | 최신 포털, 포함/제외 범위 |
| Oregon | clean decommissioning와 leak project 구분 | 공식 HOT 프로그램 및 조회 안내 | 실제 공개 조회 UI, 문서 열기, 필터·빈 결과 |
| Seattle | 주거용 탱크 폐쇄 관련 허가 기록 | 시 공식 안내/공개 데이터 확인 | API·필드·갱신·사용조건과 매칭 경계 |
| Maine | TankSmart 등록 기록 + HOSS 사건 기록 | DEP 데이터/파일실 안내 확인 | 실제 검색과 파일 요청 흐름 |
| Connecticut | DEEP spill 문서 + local 기록 구분 | 공식 온라인 문서 안내 확인 | residential 탱크와 regulated UST 구분, local 관할 |

Seattle은 Washington 전역을 대표하지 않는다. Connecticut은 주거용 탱크 전수 등록 DB로 묘사하지 않는다. Oregon은 clean decommissioning 등록과 누출 프로젝트가 다르고 오래된 기록이 온라인에 없을 수 있다. Maine 등록 기록 또한 모든 현존 탱크의 완전한 목록이라는 뜻은 아니다.

Massachusetts는 후보 조사 목록에 포함하지만 아직 같은 수준의 접근 경로가 검증되지 않았다. 다른 지역보다 늦는다는 이유로 자동 제외하는 것이 아니라, 준비되지 않은 커버리지를 약속하지 않는 것이다.

### 사람의 조사 범위와 분리

- 공개 경로 안내: 검증을 통과한 위 지역에 넓게 제공.
- founder-led 조사: 기존 NJ/NY 범위와 약속 유지.
- 다른 지역에서는 ‘직접 조회 안내 제공 / 대행 조사는 현재 지원하지 않음’을 명확히 표시. 기존 의뢰 폼을 모든 지역에 동일하게 붙여 전국 서비스처럼 보이게 하지 않는다.
- 타 지역 대행 확장은 별도 운영 검증과 사용자 결정 사항. 이를 공개 제품의 출시 조건으로 만들지 않는다.

## 7. 처음부터 강하게 출시한다는 의미

**계획 용량은 기록 관련 50~60개 수준의 유효한 공개 페이지**를 목표로 잡는다. 이는 검색량 예측도, 품질과 무관한 필수 할당량도 아니다. 기존 페이지를 포함하며 canonical 중복을 제거한 후 센다.

- 지역·관할 경로 30~40개: 기존 16개 포함. 추가 후보는 NJ/NY와 다른 검증 지역에서 조사.
- 기관·문서 작업 페이지 8~10개: 중복 의도는 병합. Oregon/Seattle처럼 자체 범위가 완결된 곳은 억지로 여러 도시로 분할하지 않는다.
- 공통 문제 페이지 6개 안팎: 기존 5개를 작업 흐름과 연결해 보강.
- 탐색·출처 설명 허브 3~5개: 목록, 범위, 방법론. 동일 역할의 기존 페이지 재사용.

위 범주는 URL별 하나의 주 역할만 배정한다. 최종 합계는 겹침과 품질 검증으로 달라질 수 있다. 독립적 내용이 부족하면 숫자를 맞추지 않고 부족분·제외 이유를 출시 명세에 공개한다. 반대로 검증할 가치가 있는 경로가 많으면 60을 상한으로 삼지 않는다.

**출시 정의:** 검증된 전체 후보군에 공통 작업 도구와 지역별 내용, 실패 상태, 내부 링크, 추적, 모바일 품질을 함께 적용한다. 한두 페이지로 공개하고 성과를 기다리는 실험이 아니다. 개발 순서는 있어도 시장 테스트를 빌미로 제품을 미완성 출시하지 않는다.

## 8. 어떤 후보를 고르는가

### 출시 범위 고정 규칙

계획 승인 후 첫 작업에서 `launch-route-inventory`를 확정한다. 각 행은 candidate_id, 기존/제안 canonical, 기관, 문서, 고유한 지역 차이, 공식 근거, UI 검증 상태, 지원 범위, KEEP/MERGE/HOLD 판정을 가진다. 그때부터 새 후보는 다음 묶음으로 보내며 이번 출시에 무한 추가하지 않는다.

조사할 지역 후보는 기존 16개와 다음 16개로 닫는다. **아래 신규 지역은 아직 검증된 서비스 지역이 아니라 조사 후보**다.

- NJ 추가 후보: Bloomfield, Glen Ridge, South Orange, Belleville, Clifton, Glen Rock, Tenafly, Jersey City.
- NY 추가 후보: Hempstead, North Hempstead, Babylon, Smithtown, Riverhead, Southampton, Yonkers, New Rochelle. Town/city/village 관할을 확인하기 전 같은 이름을 하나로 취급하지 않는다.
- 기관 작업 후보: NJDEP NFA, NJDEP 문서, NYSDEC 사건/문서, 기존 Nassau verification, Oregon clean decommissioning, Oregon leak project, Seattle residential permit, Maine TankSmart/HOSS, CT DEEP spill documents. 동일 작업이면 병합한다.
- 문제 페이지: 기존 5개 + ‘온라인 검색 결과 없음’ 1개 후보. 기존 페이지와 같은 의도라면 새 URL 없이 기존 페이지에 통합한다.

첫 제품 공개에 필요한 핵심 기록 체계는 **NJ, NY, Oregon, Seattle**이며, 기존 16개 지역의 공통 도구 적용과 이 네 체계의 완결된 사용자 경로는 빠질 수 없다. NJ/NY 추가 16개는 모두 조사·판정하고 통과한 것은 전부 같은 출시에 포함한다. 이미 알려진 공통 경로를 복제해야만 추가 지역을 만들 수 있다면 병합 사유를 기록한다.

Maine/CT는 동일 조사 묶음에 포함하되, 현재 공식 안내 이상의 검증에 실패하면 이번 공개 범위에서 명시적으로 보류한다. 이 때문에 핵심 네 체계의 출시를 무기한 미루지 않는다. 반대로 Oregon/Seattle의 핵심 작업이 검증되지 않으면 기존 16개만 출시하고 ‘넓은 피벗 완료’라고 선언하지 않고 범위 재결정을 요청한다.

최종 URL 수는 이 닫힌 후보 목록의 결과이며 50~60은 제작 용량 추정이다. 승인 시 실제 통과 목록·빠진 범위·최종 canonical 수를 제시한다. 낮은 품질로 숫자를 채우거나, 예상보다 적다는 사실을 숨기지 않는다.

월간 검색량이 아직 없는 경우도 일괄 제외하지 않는다. 다음 증거를 구분해 기록한다.

- 수요 관측: 기존 GSC의 관련 검색/노출, 실제 검색 결과의 작업 유형. 사이트 노출은 시장 전체 검색량이 아니다.
- 자료 실행 가능성: 직접 조회, 다운로드, 명확한 요청 채널, 어떤 결과를 받을 수 있는지.
- 독립적 가치: 기관 원문 하나를 다시 쓰는 것보다 무엇이 쉬워지는지.
- 유지 비용: 링크·규칙·관할 변경을 하나의 데이터 업데이트로 반영할 수 있는지.
- 적합성: 주거용 난방유 기록 작업인지, 산업용/일반 FOIL 수요가 섞이는지.

임의 점수를 합산해 객관적인 시장순위처럼 발표하지 않는다. 후보마다 ‘관측됨 / 공식 경로만 확인 / 미확인’을 표시한다. 기관 이름이 포함된 검색이라고 버리지 않되, 탱크 작업과 연결되지 않는 일반 행정 검색으로 주제를 넓히지 않는다.

## 9. 차별화와 콘텐츠 제작 기준

관공서는 원본의 권위자다. 그 권위를 대신하는 것이 아니라 **어떤 시스템에서 어떤 문서를 찾아야 하는지, 서로 다른 결과를 어떻게 구분하는지** 돕는다.

지역 페이지 출판 조건:

1. 관할과 대상 문서 명확.
2. 공식 출처 및 실제 검토 날짜.
3. 적어도 하나의 유효한 직접 조회 또는 명확한 요청 경로.
4. 검색 키/입력 필드/어디를 눌러야 하는지 구체적 설명.
5. 빈 결과·옛 기록·다른 관할의 후속 단계.
6. 무엇이 포함되지 않는지 구체적 경계.
7. 복사·인쇄·초안 등 해당 작업에 맞는 즉시 산출물.
8. 형제 페이지와 구별되는 실제 지역 정보.

실제 포털 화면을 사용하는 경우 사용권·개인정보를 점검하고 공공 화면만 사용한다. 가상 서류를 실제 사례처럼 쓰지 않는다. 공개 예시는 그 출처와 예시의 성격을 표시한다.

Google은 유용성이 낮은 대량 페이지와 같은 곳으로 보내기 위한 유사 지역 페이지를 경고한다. 따라서 이 계획의 볼륨은 지역명 교체나 키워드 변형의 수가 아니라 **완결된 서로 다른 작업의 수**여야 한다. 대량 제작이나 기능 추가 자체가 순위를 보장하지 않는다.

## 10. 디자인 방향

### 방문자 입장에서 끝까지 되는지 확인할 세 가지 장면

- **Nassau에서 제거 확인서를 찾는 집주인:** 검색으로 기존 Nassau 페이지 진입 → 새 제거 예약과 과거 verification 조회가 다름을 즉시 이해 → 필요한 주소/작업 연도 준비 → 공식 조회 → 못 찾으면 범위 제한을 확인하고 적합한 문의 초안을 복사. 회원가입·이메일 제출 없이 여기까지 완료한다.
- **Oregon에서 폐쇄 기록을 찾는 매수인:** clean decommissioning과 누출 프로젝트 중 해당 문서 선택 → Your DEQ Online의 적합한 메뉴와 검색 키 안내 → 옛 기록이면 추가 기록 요청 경로 → 발견된 프로젝트가 곧 안전 인증이라는 오해 없이 다음 서류를 확인. NJNY 조사 의뢰로 억지 유도하지 않는다.
- **NJ에서 판매자가 준 종이를 확인하려는 매수인:** 문서가 municipal permit인지 NFA인지 스스로 선택하도록 명확한 예시 제공 → ‘발급됨’과 ‘검사/작업 완료’를 분리한 체크리스트 → 추가로 구해야 하는 원본과 관할 안내 → 필요하면 기존 대행 의뢰. AI가 서류 내용을 읽고 판정한 것처럼 표시하지 않는다.

### 구체적 동작 예시 — 실제 고객이 아닌 합성 시나리오

**Nassau 예시:** 사용자가 `Nassau / historical removal or abandonment verification / work year known`을 선택한다. 결과는 `새 작업 예약이 아닌 Print Verification Letter 경로`, 준비할 `property address, municipality, approximate year`, 작업지의 `주소 일치 / 작업 종류 / 날짜 확인` 항목이다. `온라인 결과 없음`을 누르면 같은 링크만 다시 보여주지 않고 `공개 조회에서 찾지 못함; 실제 기록 부재는 미확정`으로 상태가 바뀐다. 초안은 `I am seeking an existing removal or abandonment verification record for [address], approximately [year]. The public verification search returned no match. Please identify the appropriate search or records-request route. This is not a request to schedule new tank work.`로 조합한다. 기존 사이트 대비 추가 가치는 문서 목적 선택과 결과에 따른 작업지·초안 변경이다. 주소나 연도가 없어도 무엇이 빠졌는지 보여주고 조사 의뢰를 강요하지 않는다.

**Oregon 예시:** 사용자가 `Oregon / clean decommissioning / project before April 3, 2024`를 선택한다. 결과는 leak project 검색과 분리된 `Permits/Licenses/Certificates → HOT Clean Decommissioning → HOT Decommissioning`, 검색 키 `house number + street name`, `옛 자료가 온라인에 없을 수 있음` 안내다. 사용자가 `누출 프로젝트를 찾음`으로 돌아오면 clean decommissioning 완료로 체크하지 않고 다른 문서 종류로 보관한다. `온라인 결과 없음`이면 초안은 `Please provide existing heating-oil-tank clean decommissioning records for [address], approximately [year], and reference [DEQ number if known]. The online public search did not return the requested file.`로 조합한다. 이 지역에서는 직접 조회·요청 준비로 완료되며 NJNY 대행 제출을 기본 다음 단계로 보여주지 않는다. 예시 메뉴는 공식 안내에 근거하며 실제 UI 검증 전 최종 화면 문구로 확정하지 않는다.

이 두 경로를 개발 환경에서 입력→결과→실패 후 조치까지 시연할 수 있어야 다른 지역으로 공통 모듈을 확장한다. 이는 내부 품질 게이트이지 두 페이지만 공개하는 시장 실험이 아니다.

현재 화이트/딥그린, 자체 호스팅 폰트, 브랜드, 개선된 헤더를 유지한다. 오래된 레이아웃 위에 새 카드만 붙이는 방식은 사용하지 않는다.

- 홈: 짧은 설명 + ‘어느 지역 / 어떤 서류’ 작업 시작. 큰 사진은 작업을 밀어내지 않는 보조 요소.
- 기관·지역: 첫 화면에 찾는 기록, 현재 조회 경로, 핵심 제한. 의뢰 폼은 결과 옆 선택지 또는 아래 섹션.
- 결과: ‘권장 출처 / 검색 키 / 다음 행동’이 중심. 안전 점수·가짜 증명서·과도한 대시보드 지양.
- 모바일: 고정 헤더가 결과나 버튼을 가리지 않도록. 320/390/768/800/960/1440px에서 메뉴·복사·인쇄·오류·긴 기관명 확인.
- 키보드, 명확한 focus, aria-live 결과, 최소 44px 터치 영역, reduced motion, JavaScript 없이 원문 경로 열람 가능.

이것은 재브랜딩이 아니라 화면의 주인공을 ‘소개’에서 ‘사용자의 작업’으로 옮기는 구성 변화다.

## 11. 기존 코드 활용과 제안 구조

| 현재 자산 | 활용 | 필요한 변경 |
| --- | --- | --- |
| ResearchCatalog / AdditionalResearchAreas | 지역·문제 콘텐츠, 기존 URL 유지 | 관할·문서·지원 범위의 안정적 ID 추가; 중복되는 출처 필드 통합 |
| RecordsDataRepository / lookup-sources.json | 공식 경로와 persistent override 유지 | 화면과 도구가 같은 원천을 읽게 하고 검토 상태 노출 |
| researchDetail / records JTE | SSR 안내 재사용 | 공통 작업 영역과 반환 상태 추가 |
| site-v2.js / app.js | 복사·분석·intake 재사용 | 경로선택/작업지 상태는 분리된 모듈, 중복 이벤트 금지 |
| 기존 intake / private case ledger | NJNY 대행 선택지 유지 | 지원 범위 표시, 사용자 동의 시에만 작업 정보 전달 |
| 기존 20 utilities | 기존 검색 자산 보존 | 정말 관련된 결과에서만 기록 안내 링크 |

```text
검증된 공개 경로 데이터 + 검증된 override
       ├── SSR 기관/지역/문제 페이지 ── 검색엔진·일반 방문자
       └── 동일 경로의 최소 클라이언트 데이터 ── 작업 도구
                                                  ├── 공식 사이트 열기
                                                  ├── 로컬 초안/인쇄/상태
                                                  └── 동의 + 지원지역 확인 → 기존 private intake

private case ledger ── 공개 데이터로 직접 노출 금지
                  └── 운영 절차를 거친 비PII route lesson만 검토 후 반영
```

Spring Boot/JTE 및 file-backed data를 유지한다. 새 SPA, 계정 시스템, 관계형 DB, 별도 운영 CRM을 도입하지 않는다. 초기 입력은 관할 직접 선택으로 완결되므로 지도/주소 API 장애가 전체 제품을 멈추지 않는다.

공개 경로 레코드 추가 제안: stable route_id, jurisdiction_id, document_type, supported_tank_scope, access_mode, official_url, required_identifiers, result_semantics, record_coverage, fallback, verified_at, review_due, support_mode, evidence_reference. 모르는 값은 unknown이며 임의 기본값으로 확정하지 않는다.

현재 override의 composite key를 새 ID로 일괄 교체하지 않는다. 기존 파일을 읽을 수 있는 호환 매핑·충돌 테스트 후 도입하며 배포가 persistent 데이터를 덮어쓰지 않게 한다.

## 12. 오류·위험·검증 계약(설계 제안)

아래는 구현 완료 상태가 아니라 구현 시 필요한 계약이다. 예외 이름은 구현 경계에서 확정한다.

| 경로/오류 | 처리 | 사용자 표시 | 필수 검증 |
| --- | --- | --- | --- |
| 관할/문서 미선택 또는 빈 문자열 | 선택 요청; false default 금지 | 무엇을 선택해야 하는지 | null/empty/unsupported enum |
| 같은 도시명·village/municipality 경계 모호 | 자동 확정 중단 | 관할 확인 필요, 선택지 | 동일 명칭·우편도시 fixture |
| 알려진 경로 없음 | 상위 기관 안내만, 검색 완료 아님 | 아직 검증된 지역 경로 없음 | zero routes |
| 공식 포털 실패/403/로그인 | 독립된 접근 실패 상태 | 대체 요청 경로 | 외부 장애를 no-record로 바꾸지 않음 |
| 날짜 경과/링크 이동 | reviewed/due와 제한 노출 | 경로 재확인 필요 | 고정 날짜 clock 기반 테스트 |
| JSON 파싱/필수값 오류 | bundled baseline 유지 + admin warning | 필요한 경우 제한된 안내 | invalid override/중복키; 기존 동작 보존 |
| sessionStorage/localStorage SecurityError/QuotaExceededError | 저장 포기, 현재 작업 계속 | 저장 불가; 복사/인쇄 가능 | private browsing/quota |
| clipboard NotAllowedError | 선택·수동복사 fallback | 복사되지 않음 | denied permission |
| 입력에 HTML/script, 지나친 길이 | escape/길이 제한 | 입력 수정 안내 | XSS/Unicode/oversize |
| 재클릭/뒤로/새로고침 | idempotent state; 작업 복원 | 상태 일관성 | repeat/back/reload |
| 미지원 지역에서 대행 요청 | 지원 범위 명시, 자동 수락 금지 | 직접 조회만 지원 | 타지역 CTA 테스트 |
| 분석 요청 실패/차단 | 제품 동작 계속 | 사용자 방해 없음 | analytics disabled |

주소·사건번호·문서 원문을 telemetry에 넣지 않는다. 요청문은 로컬 문자열 생성이며 임의 URL fetch·파일 경로·LLM 실행으로 연결하지 않는다. 공개 예시는 개인 주소 검색을 대신 수행하지 않고 synthetic fixtures로 개발한다. 직접 데이터 어댑터는 rate limit, 이용조건, match semantics, 데이터 최신성을 별도 검증하기 전 활성화하지 않는다.

```text
기본 → 선택 완료 → 경로 준비 → 공식 사이트 방문(자기 보고)
                              ├→ 찾음(사용자 보고) → 서류 확인 체크리스트
                              ├→ 빈 결과 → 추가 검색/기록 요청 초안
                              ├→ 접근 실패 → 대체 채널
                              ├→ 다른 관할 → 관할 재선택
                              └→ 요청 대기 → 대기 상태 유지
어떤 상태도 자동으로 '안전', '탱크 없음', '공식 완료'가 되지 않음
```

## 13. 출시 전 완료 기준

### 유지보수가 다시 병목이 되지 않게

- 운영 책임은 현 서비스 소유자에게 있다. 에이전트가 검토를 도울 수 있지만 상시 자동 운영을 하고 있다고 가정하지 않는다. 별도 외부 인력 고용을 출시 조건으로 만들지 않는다.
- 출처 간 모순이나 잘못된 관할이 확인되면 해당 직접 실행 버튼/초안을 비활성화하고, 안전한 설명과 확인 가능한 상위 출처는 유지한다. 단순 기한 경과는 정정 필요 표시, 실제 오안내는 동작 제한으로 구분한다. 유용하고 정확한 설명도 유지할 수 없으면 페이지 처리/대체 URL을 검토하며 자동 대량 삭제는 하지 않는다.
- 닫힌 후보 인벤토리를 확정한 뒤 출처 3종(직접 조회형/요청형/복합형)을 실제로 갱신해 소요 시간을 측정한다. 이를 기반으로 초기 조사 총량과 월간 유지 시간을 산정하고 사용자가 감당할 수 있는지 확인한다. 근거 없는 ‘유지보수 거의 없음’이나 임의 시간 예산을 약속하지 않는다. 감당할 수 없으면 같은 기관을 공통화하거나 낮은 가치의 중복 범위를 줄이고, 변경 규모를 보고한다.

- URL 하나와 기관 절차 하나를 하나의 source/route 레코드로 유지하고 이를 여러 페이지가 참조한다. 같은 안내를 50개 파일에서 수작업 수정하지 않는다.
- 알려진 포털 이전은 그 날짜에 재검토하도록 표기하고, 일반 경로는 기본 90일 검토 주기를 계획한다. 모든 포털이 90일 안전하다는 보장은 아니다. 정책·마감·수수료처럼 영향이 큰 항목은 더 짧은 주기를 지정한다.
- 링크 상태 확인과 절차 유효성 확인은 다르다. HTTP 200이나 로그인 화면이 나온다는 이유로 verified_at을 자동 갱신하지 않는다.
- 일시적 장애나 검토 기한 도달만으로 자동 삭제/noindex하지 않는다. 직접 조회 실패와 검토 기한을 표시하고 검증된 fallback을 유지한다. 지원 불가능한 약속은 즉시 숨기거나 정정한다.
- admin에 overdue sources, invalid override, broken route, unsupported intake를 한 목록으로 보여준다. 새로운 별도 운영 대장을 만들지 않는다.
- 첫 출시 전 실제로 최소 한 번 ‘포털 링크 변경 → 공통 데이터 수정 → 관련 페이지 전체 반영 → 회귀 테스트’ 리허설을 한다. 페이지 수보다 이 작업이 감당되는지 확인한다.
- 이번 계획 작성으로 스케줄러·외부 알림·자동 발송을 생성하지 않는다. 향후 소스 점검 자동화는 별도 구현 명세에 입력·오류·허용 호스트를 포함한다.

- 선정된 모든 경로의 출판 조건을 통과. 문서 출처 검토와 실제 포털 동작 검증을 별도 표시.
- 대표 기능 fixture뿐 아니라 모든 데이터 레코드에 schema/ID/URL/지원범위/required field 검증.
- 6개 대표 작업 E2E: NJ NFA, Nassau, Oregon clean, Oregon leak, Seattle, 미지원 관할. 실제 외부 신청/발송 없이 검증.
- no-JS 읽기, 키보드, 모바일, 복사 실패, 저장 실패, 되돌아가기, 미지원 지역 검증.
- 전체 sitemap URL 상태/자기 canonical/noindex 모순/중복 intent/내부 링크 점검.
- 원래 기록 URL/utility/의뢰 기능 회귀 테스트. 특별한 중복 근거 없이 삭제·301하지 않는다.
- 실제 GA4 수집과 내부 이벤트를 별도로 확인. 이벤트 이름 존재만으로 수집 성공이라고 하지 않는다.
- private storage·override 백업, 기존 케이스 상태 불변, 알림 자동 발송 없는지 점검.
- Brookhaven 포털 변경을 재검토하고 오래된 ‘예정’ 설명 수정.
- incident override의 현재 조용한 fallback도 운영 가시성 보강 대상으로 명시. 이번에는 수정하지 않았다.

## 14. 개발·배포 순서

1. **검색·경로 설계:** 후보 인벤토리, 실제 검색 작업, 대표 URL, 중복/지원범위 확정.
2. **공통 데이터·도구:** 하나의 경로 모델과 SSR 페이지, 선택·초안·결과 상태 구현.
3. **전체 콘텐츠와 화면:** 기존 16개와 검증된 추가 경로를 함께 채우고 모든 템플릿에 적용.
4. **검증:** SEO/접근성/오류/프라이버시/기존 기능/운영 호환성 확인.
5. **하나의 제품으로 공개:** 기술적 배포는 쪼갤 수 있으나 대외 공개는 완결된 묶음. 기존 사이트를 장기간 미완성으로 노출하지 않는다.

```text
확정된 원천/URL → 호환 데이터 → SSR+도구 → 전체 콘텐츠 → QA
 → private backup → 앱 배포 → smoke check → 새 sitemap 1회 제출
                                          └ 실패 → 이전 앱/데이터 호환 버전 복귀
```

수정된 실제 URL만 색인 요청 후보로 삼고 같은 URL을 반복 신청하지 않는다. 백업된 운영 케이스 데이터는 새 intake를 잃게 하는 과거 스냅샷으로 무조건 되돌리지 않는다. 공개 UI/코드 rollback과 운영 데이터 복구를 분리한다.

연구·검증 시간은 아직 미산정이다. 원천 포털 접근, 데이터 이용조건과 실제 지역 수가 확정되기 전 ‘AI로 몇 시간’ 같은 완료 약속을 하지 않는다. 자동화로 줄일 수 있는 코드 작업과 사람이 확인해야 할 출처 작업을 분리해 인벤토리 확정 후 산정한다.

## 15. SEO 성과 판정과 실패 시 대응

### 두 가지 성과를 혼동하지 않는다

**NJ/NY:** 관련 organic 유입 → 직접 해결/대행 선택 → 유효 의뢰 → 유용한 전달 → 향후 수익·노동 비용. 이 경로가 기존 사업 모델의 검증 대상이다.

**그 외 self-service 지역:** 관련 organic 유입 → 조회/요청 준비를 실제로 사용 → 자체 해결의 자기 보고 및 실패 패턴 → 유지 비용. 이 지역의 방문 증가만으로 기존 대행 사업이 성공했다고 평가하지 않는다. 공식 링크 클릭만으로 해결 완료라고 집계하지 않는다.

타 지역은 8~12주 누적 점검에서 관련 검색 유입과 작업 이용이 반복되는지, 최신성을 유지하는 비용이 감당되는지 본다. 긍정적이면 기존 범위를 유지·개선하고, 관련 유입이나 실제 작업이 거의 없는데 관리 비용만 높으면 원인을 조사한 뒤 추가 확장을 중단한다. 바로 지역 페이지를 삭제하는 규칙은 아니다. 실제 타 지역 의뢰 의사나 반복되는 실패 수요가 관측될 때만, 별도 승인으로 대행 범위 또는 수익화 방식을 검토한다. 방문자 수가 많다는 이유로 이를 자동 승인하지 않는다.

| 관측 | 해석 | 다음 작업 |
| --- | --- | --- |
| 미발견/미수집 | 노출 기회 자체 미확보 | 링크·sitemap·응답·canonical 점검 |
| 수집됐지만 상당수가 미색인 | 중복/얕음/품질/기술 가설 | 대표 페이지 비교, content distinctness 점검 |
| 색인됐으나 관련 노출 거의 없음 | 수요·타깃·경쟁력 가설 | 검색 결과/쿼리/기관별 비교; 검색량 0 단정 금지 |
| 관련 노출 있으나 클릭 적음 | 순위·의도·제목·공식사이트 선호 혼합 가능 | query mix와 position을 함께 확인 |
| 클릭 있지만 작업 시작 적음 | 답만 보고 해결했거나 UX 불일치 | 직접 링크 클릭과 도구 사용을 분리 |
| 도구 사용·공식 이동 있으나 의뢰 적음 | 셀프서비스 해결 또는 대행 가치 미입증 | 유입 실패로 혼동하지 않음 |
| 관련 유입·의뢰 증가 | 획득과 수요 신호 | 실제 유용한 전달·운영 비용 별도 검증 |

측정 단위: 기관/문서 family, 지역 route_id, 공개 self-service 지원과 대행 지원의 구분. 비교는 완전한 14/28일 창, 8~12주 누적 점검으로 제안하되 SEO 반응의 보장 기한으로 사용하지 않는다. 신규 URL은 출시일·최초 관측 crawl을 기록하고 기존 URL과 구분한다. 평균 순위와 전체 노출만으로 성공을 선언하지 않는다.

이벤트 제안: route_selected, official_route_opened, request_draft_copied, worksheet_print_requested, search_outcome_reported, assist_cta_clicked, 기존 server-confirmed research intake. print 요청은 인쇄 완료가 아니고, official click은 파일 확보가 아니다. route_id/document_type/outcome만 분석 도구로 전송한다.

예상 매출을 산정할 데이터가 없으므로 수익 예측을 제시하지 않는다. 이번 계획의 1차 검증은 관련 검색 유입, 2차는 실제 작업 가치, 3차는 기존 대행 서비스의 지속 가능한 수익 가능성이다. SEO만으로 고객을 얻는 것과 자동으로 수익이 나는 것은 다르다.

## 16. 하지 않을 것

- 다시 이름·도메인·전체 프레임워크 변경.
- 산업용 UST·일반 부동산·난방 전반으로 무제한 주제 확장.
- 모든 지역×모든 질문을 자동 생성.
- 공개 데이터가 비어 있는데 안전/탱크 없음 결과 제공.
- 미검증 전국 조사 대행 약속, 새 요금·결제 도입.
- 타인의 고객 사례나 정부 서류를 자체 수행 증거로 제시.
- 무단 데이터 수집·CAPTCHA 우회·자동 기관 발송.
- 클릭이 생길 때까지 기능/콘텐츠를 미완성으로 유지.

## 17. 12개월 방향과 승인 사항

```text
현재: 16개 안내 + 사람에게 의뢰
  → 제안: 여러 기록 생태계 + 완결된 self-service + 선택적 NJNY 대행
  → 장기: 관측된 수요와 검증된 원천 중심으로 데이터 연결/대행 범위 확장
```

사용자에게 권고하는 결정은 **B: 기록 조회 작업 서비스로의 공개 제품 피벗**이다. 지역 범위 확대, 홈의 작업 중심 재구성, 약 50~60개 기록 페이지 용량은 아직 제안이다. 승인 전 기존 운영 지침을 바꾸지 않는다.

주요 미해결 사항: 외부 검색량/경쟁 조사, 후보군별 실제 포털 동작, 추가 경로의 최종 수, OR/Seattle/ME/CT의 출판 가능 범위. 이것들은 소량 A/B 실험의 이유가 아니라 출시 전 조사 명세다.

### 독립 제안서 검토

- 2회 검토: 첫 검토의 4개 지적(닫힌 출시 범위, 유지 책임/비용, 기존 기능 대비 실제 추가 가치, 지역별 사업 성과 분리)을 반영했고 두 번째 검토에서 해당 범위 PASS.
- 검토 점수 9/10은 문서의 일관성·완결성 평가일 뿐 시장 수요, 외부 자료 정확성, 구현·배포 준비도를 검증하지 않는다.
- 상태: DONE_WITH_CONCERNS — 계획 제안 작성 완료. 사용자 범위 승인과 공식 포털 동작/후보 지역 검증은 남아 있다. 기술·디자인 상세 검토는 구현 전에 필요하다.
